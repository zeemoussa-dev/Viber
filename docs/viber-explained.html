1The problem and the idea

Claude forgets everything between sessions. On a big project you also run several sessions at once. Notes kept in markdown files go stale, and two sessions can edit the same file without knowing.

Before

Every session reads and rewrites files. They disagree and drift.

With Viber

Sessions call one service. Rows in a database are the single source of truth.

One sentence: Viber gives every Claude session a shared, searchable memory of the project, plus a map of how its parts depend on each other.

4What a new session is told

At start, Viber hands the session a short context pack. It has a token budget (default 1,500). Sections are added in priority order, and what does not fit is dropped from the end. Drag the budget to see what survives. The line counts below are an illustrative example, not real data.

"For now" facts (temporary instructions that end by themselves) go first, so they are the last thing the budget can cut. The newest handoff is kept whole (up to 2,000 characters); older ones are shortened to 600.

5Memory and human review

Claude can write a lot, but it cannot make something binding. A rule or decision that a session proposes waits until a person accepts it.

Who may do what

Four roles, each includes the ones to its left. Click a role. Tokens can also be limited to certain projects.

ActionNeedsAllowed?

Sessions are meant to use a write token. If no master token is configured, Viber runs open (local development only).

6How recall finds things

When Claude calls viber_recall, Viber runs up to three searches and merges them by rank, not score (reciprocal rank fusion, k=60). Something found by several searches beats something found by one. Toggle the searches to see the effect. The items below are made up.

Fused result

Rules get a 1.3 boost. A rule that covers only some components is shown as [only for a, b], and a temporary fact as [temporary, until ...], so neither reads as permanent or global. Text that looks like a secret is never sent to the embedding model.

7The code map: components and links

Separately from memory, Viber keeps a map of which parts depend on which. A scanner feeds it manifest files (pyproject.toml, package.json and a few others). Code reads the manifests and solves the version ranges. A model never decides a link. The names here are an example.

  • verified: the manifest says so. drifted: it used to, and no longer does.
  • GET .../links/check reports drifted links, unsatisfied constraints, unprovided contracts and unversioned targets.
  • GET .../components/{key}/impact?version=X walks the dependents breadth-first and says which would break at X. Dev-only dependencies are ignored.
  • A head version is the latest scan of the default branch and gets overwritten; a release comes from a tag and never changes.

9Rules of the road

Rows, not files.

Nothing long is stored. A fact is at most 500 characters, a rule 400, an episode 1,000, a spec row 400, a decision statement 500. Longer text is refused or split. File claims were built and then dropped, because rows need no locking.

One project never sees another.

Every query filters by project, links cannot cross projects, and a token can be limited to chosen projects. A session in a folder no project owns writes nothing.

Migrations are append-only.

Numbered SQL files run in order at startup under a lock. Add a new one. Never edit one that has shipped.

Everything is audited.

Every write records who did it. A named token is its own actor; otherwise it comes from the X-Viber-Actor header.

Safe to repeat.

Imports and hook writes use ON CONFLICT DO NOTHING, keyed by key or source + source_ref. Dry runs roll back after counting.

Tests run in Docker, on a real Postgres.

The suite drops and recreates a viber_test database, never your dev data. src/ is copied into the image, so Python changes need --build.

Heads up: SPEC.md is the original design and is out of date. Trust the README and the code.

10Run it

Everything runs in Docker. Nothing needs installing on the host.

Start the database and API (dashboard at http://localhost:8088, API docs at /docs)
docker compose up -d --build
Run the full test suite
docker compose --profile tests run --rm --build tests
Run one test file, filtered
docker compose --profile tests run --rm --build tests pytest -q tests/test_map.py -k drift
Dashboard with hot reload (needs the API container up)
cd dashboard; npm install; npm run dev
Connect Claude Code to the MCP tools
claude mcp add --transport http viber http://localhost:8088/mcp

The first start pulls a ~1.2 GB embedding model. Set VIBER_EMBED_PROVIDER=none for keyword-only recall and a fast start.
